# Поведение приложения и контракты

Этот документ описывает текущую реализацию. Автоматизированные проверки и их ограничения перечислены в
[e2e-testing.md](e2e-testing.md). Архитектура модулей и правила изменений — в [AGENTS.md](../AGENTS.md).

Историческая E2E-спецификация добавлена в
[PR #51](https://github.com/alad1nks/dubovozki-kmp/pull/51) и удалена при внедрении набора в
[PR #52](https://github.com/alad1nks/dubovozki-kmp/pull/52). Она описывала целевое покрытие, а не доказательство
выполнения каждого сценария. Более поздние изменения поведения имеют приоритет: например,
[PR #58](https://github.com/alad1nks/dubovozki-kmp/pull/58) удалил карточку ближайшего автобуса.

## Навигация

- Стартовый экран — расписание автобусов. Верхний уровень: расписание, сервисы, настройки.
- При ширине меньше `600.dp` используется bottom bar; от `600.dp` — navigation rail.
- В расписании кастелянной верхнеуровневая навигация скрыта. Back возвращает к сервисам.
- Переходы верхнего уровня используют `launchSingleTop`, `saveState` и `restoreState` в `AppState`.
  Смена языка пересоздаёт Compose content, сохраняя общий navigation controller.

## Автобусы

- По умолчанию выбраны «Сегодня», «Все станции», направление «В Москву».
- Направления переключаются нажатием вкладки или swipe. Фильтры станции и дня применяются одновременно.
- Расчёты дня и относительного времени используют Москву (UTC+3), независимо от часового пояса устройства.
  `MoscowTimeProvider` обновляет время на границе минуты; смена дня обновляет фильтрацию.
- День Firebase `2` означает понедельник, `3` — вторник–пятницу, `7` — субботу, `1` — воскресенье.
  «Будни» выбирает группу `3`; «Завтра» в воскресенье выбирает понедельник (`2`).
- Станции: `odn` — Одинцово, `slv` — Славянский бульвар, `mld` — Молодёжная.
  Направления: `msk` — в Москву, `dbk` — в Дубки. `dayTime` — миллисекунды от начала московского дня,
  `dayTimeString` — отображаемое время.
- Mapping пропускает записи без обязательных значений и с неизвестным днём/станцией/направлением.
  Порядок рейсов сохраняется из источника; backend должен выдавать хронологический список с уникальными ID
  внутри отображаемого списка.
- Относительное время показывается только для «Сегодня». Первое открытие списка, смена фильтра и обновление
  данных прокручивают его к первому не ушедшему рейсу. Ежеминутное изменение времени не сбрасывает прокрутку.
- После последнего рейса список остаётся доступен; отдельного сообщения «рейсов больше нет», карточки ближайшего
  рейса и кнопки «К ближайшему» сейчас нет. Нет и отдельной метки времени свежих данных над списком.
  При offline-состоянии время cache показывается в баннере.
- Пустой результат показывает действие сброса к «Сегодня» и «Все станции». Refresh сохраняет выбранные фильтры.

Основные файлы: `core/domain/.../GetBusScheduleImpl.kt`, `feature/busschedule/.../BusScheduleViewModel.kt`
и `BusScheduleScreen.kt`.

### Напоминания

Долгое нажатие на будущий рейс в режиме «Сегодня» открывает диалог. Можно ввести целое число минут от нуля
до оставшегося количества полных минут. Диалог обновляет ограничение раз в секунду; прошедший рейс недоступен.
По умолчанию предлагается уведомление за 10 минут или меньше, если до отправления осталось меньше времени.

| Платформа | Будильник | Локальное уведомление |
|---|---|---|
| Android | Intent системному приложению часов | AlarmManager и notification receiver; POST_NOTIFICATIONS на API 33+ |
| iOS | Недоступен | UserNotifications с запросом разрешения |
| JVM / Web | Недоступен | Недоступно |

На Android без доступа к exact alarms текущая реализация использует неточный `setAndAllowWhileIdle`:
уведомление может опоздать. Напоминания Android не восстанавливаются после перезагрузки устройства.
Недоступные методы видны в диалоге, но отключены. Фактическая доставка системных напоминаний пока не покрыта E2E.

## Сервисы и кастелянная

- Пункт кастелянной доступен даже при загрузке или ошибке внешних ссылок.
- `contactLink` и `donutLink` открываются через `LocalUriHandler`. UI допускает `http://`, `https://`,
  `mailto:` и `tg://`; остальные или отсутствующие ссылки скрываются. Это фильтр схем, а не полная проверка URI.
  Ошибка открытия показывает snackbar.
- Расписание кастелянной содержит независимые списки для корпусов 1, 2, 3. Дни используют ISO-нумерацию
  `1` (понедельник) … `7` (воскресенье), отличающуюся от автобусной схемы.
- Repository пропускает дни вне `1..7`, строки без дня/времени и пустое время, удаляет точные дубликаты
  `(day, time)`. Это применяется к ответу API и к ранее записанному cache. Остальные строки сохраняют порядок.
  `time` — текст, поэтому допустимы диапазоны времени и обозначение выходного дня.
- Текущий московский день выделяется. При изменении списка или дня выполняется прокрутка к нему,
  если его индекс больше нуля. Пустой корпус показывает своё сообщение; другие корпуса остаются доступны.
- Refresh и realtime обновляют данные, сохраняя выбранный корпус.

## Firebase, cache и ошибки

Paths: `busSchedule`, `services`, `servicesSchedule/linenRoom`. DTO находятся в `core:firebase`, mapping —
в `core:data`. Добавление/изменение backend schema требует отдельного запроса.

| Платформа | Получение данных | Refresh |
|---|---|---|
| Android / iOS / JS | Первое значение и последующие события Firebase SDK | Удалить предыдущий listener и подписаться заново |
| JVM | Одно REST-чтение при создании соответствующего API | Отменить предыдущую задачу и выполнить новый GET |

Неизвестные JSON-поля допускаются JS/iOS/JVM adapters; Android SDK пропускает дополнительные поля при mapping.
Невозможность разобрать ответ превращается в `Data.Error`. Отказ в доступе Firebase также передаётся как ошибка,
в том числе через iOS `withCancelBlock` согласно
[контракту Firebase](https://firebase.google.com/docs/reference/ios/firebasedatabase/api/reference/Classes/FIRDatabaseReference).
Отмена старого JVM-запроса при refresh не публикуется как ошибка нового запроса.

Repository сначала читает сериализованный cache, затем подписывается на API:

| Cache / ответ API | Состояние UI |
|---|---|
| Cache отсутствует, ответ ещё не получен | Loading |
| Есть cache, API ещё загружается | Сохранённое содержимое без offline-баннера |
| Нет cache, API вернул ошибку | Error и Retry |
| Есть cache, API вернул ошибку | Содержимое cache и offline-баннер с сохранённым временем |
| Успешный ответ, включая пустой | Новое содержимое, обновление cache и времени получения |
| Cache повреждён и не декодируется | Cache игнорируется; состояние определяется API |

Время cache — локальное время получения ответа, не backend revision. Firebase SDK может продолжать отдавать
локальные данные при потере сети без error callback; offline-баннер не является индикатором сетевого подключения.
Кэширование делает данные доступными после успешной загрузки, но не создаёт расписание при первом запуске offline.

## Настройки и хранение

- Тема: System, Light, Dark. Новое значение `theme_mode` имеет приоритет над legacy `dark_theme`.
  Без обоих значений используется System.
- Язык: System, русский, English, қазақ тілі. Неизвестный сохранённый код выбирает System.
- Русские Compose-ресурсы лежат в `values`, переводы — в `values-en` и `values-kk`.
  Собственные названия трёх языков определены только в default XML и используют resource fallback.
- Web синхронизирует title и HTML `lang` с выбранным языком; System учитывает язык браузера, включая
  региональные `en-US`, `kk-KZ`, `ru-RU`.

Ключи storage: `language`, `theme_mode`, legacy `dark_theme`, `bus_schedule_cache_v1`, `services_cache_v1`,
`services_schedule_cache_v1`. Android/iOS/JVM используют DataStore (`dubovozki.preferences_pb`), Web — localStorage.
Android хранит файл в `filesDir`, iOS — в Documents, JVM — в системной временной директории. Поэтому на Desktop
настройки/cache переживают обычный повторный запуск, но могут исчезнуть при очистке временных файлов ОС.
На Web данные привязаны к origin и исчезают при очистке данных сайта.
